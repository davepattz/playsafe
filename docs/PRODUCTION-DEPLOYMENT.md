Keep the native archive and roles export in protected storage outside Git. The database archive SHA-256 is `2D09459D84957A123298D3CC9E56BDBBF3FA4F091F86A73D6AADDEA19559365E`. [Supabase backup and restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)

2. Create a fresh backup or verified recovery point with a timestamp and protected storage location. Verify recoverability by restoring into an isolated recovery target and checking the V1 data, grants, extensions, and required custom roles. This is a backup verification exercise and does not require a publicly accessible staging website. If the project uses Storage, preserve its objects separately. Record restore scope and evidence. Avoid activating copied jobs or external webhooks in a recovery instance. [Supabase database backups](https://supabase.com/docs/guides/platform/backups) · [Restore to a new project](https://supabase.com/docs/guides/platform/clone-project)
3. Rehearse the migration against that verified schema. Verify that V1 records, grants, API reads and existing jobs are preserved. Only then apply the V2 migration once to the approved target and record the migration version. Validate V2 table/index availability, RLS and privileges through PostgREST, and verify persistent reports, UTC popularity increments and a shared quota using separate instances.
4. The shared-role migration creates `playsafe_v2_app` with login disabled. Provision its generated password outside SQL migration history and enable login only after verifying the V1 cache ACL. Configure `V2_SUPABASE_MODE=shared-production`, `V2_SUPABASE_URL`, `V2_SUPABASE_ALLOWED_ORIGIN`, `V2_SHARED_DATABASE_CA` and the secret `V2_SHARED_DATABASE_URL` in Netlify's production context, using Functions-only scope where the plan supports it. Both origin settings must match the existing PlaySafe project. Use the shared Supavisor transaction pooler, port 6543, and username `playsafe_v2_app.<project-ref>`. Set the CA variable to the base64-encoded PEM certificate published by Supabase Studio. Leave `V2_SUPABASE_SERVICE_ROLE_KEY` unset in this mode. Retain the existing V1 variables. The driver verifies the CA and hostname and uses bound values with fixed V2 SQL. [Supabase database connections](https://supabase.com/docs/guides/database/connecting-to-postgres) · [Supabase TLS configuration](https://supabase.com/docs/guides/platform/ssl-enforcement)
5. Verify a dedicated role session cannot modify V1, can access V2 via RLS, and can use the actual pooler endpoint. The [shared-role rollback](../supabase/rollback-v2-shared-project-role.sql) revokes shared access and leaves all application data intact. Disable the shared runtime settings and drain connections before using it.

The current Netlify plan rejects explicitly selected environment scopes. Use the provider's default secret scopes and explicitly select the production deploy context. The protected connection string is available internally to production builds and server code under that plan. The adapter is server-only and the setting must never use a `NEXT_PUBLIC_` prefix. Before publishing, verify that preview contexts lack the secret and check that the client bundle does not reference the shared connector or environment variable. The provider excludes post-processing from secret settings. These checks passed before the V2 merge was pushed.

### Recovery scope

The restored public schema contained the V1 cache and Supabase's RLS automation function. The production inventory found no application table triggers, Realtime public tables, database Cron relation, deployed Edge Functions, Auth users, Storage buckets or objects, or Vault secrets. The isolated recovery reproduced the production API roles and schema access, restored all four V1 rows, and ran both migrations and their SQL checks. The shared-role reversal preserved the legacy row digest, ACL and RLS. The rehearsal did not restore provider-managed extensions or global role passwords onto the plain PostgreSQL instance.

For platform recovery, restore Supabase's managed schemas and extensions through a compatible Supabase target and reconfigure its project settings and API keys separately. If the project later uses Storage objects, Edge Functions, Auth configuration, Realtime or external scheduled jobs, include their separate recovery procedures. The V1 request-driven cache maintenance stays in the existing code and configuration. [Supabase recovery scope](https://supabase.com/docs/guides/platform/migrating-within-supabase/dashboard-restore)

### Database backup and compatibility gate

1. Identify the production Supabase project and read the existing extension placement, table and function names, V1 schema and grants, jobs, API exposure and connection method. Record their state without changing anything. Verify whether the V2 tables or migration history already exist.
2. Create a fresh backup or verified recovery point with a timestamp and protected storage location. Verify recoverability by restoring into an isolated recovery target and checking the V1 data, grants, extensions, and required custom roles. This is a backup verification exercise and does not require a publicly accessible staging website. If the project uses Storage, preserve its objects separately. Record restore scope and evidence. Avoid activating copied jobs or external webhooks in a recovery instance. [Supabase database backups](https://supabase.com/docs/guides/platform/backups) · [Restore to a new project](https://supabase.com/docs/guides/platform/clone-project)
3. Rehearse the migration against that verified schema. Verify that V1 records, grants, API reads and existing jobs are preserved. Only then apply the V2 migration once to the approved target and record the migration version. Validate V2 table/index availability, RLS and privileges through PostgREST, and verify persistent reports, UTC popularity increments and a shared quota using separate instances.
4. The current V2 adapter refuses a URL whose origin matches configured V1 Supabase variables. A dedicated V2 production project within the existing Supabase organisation can satisfy the current isolation check. If V2 must share the V1 project, agree on and verify an explicit compatibility change before deploying. Do not remove V1 settings or bypass the check by using an alias for the same project.

### Public deploy and rollback gate

1. In Netlify, preserve the V1 deploy ID and confirm a permitted operator can republish it. Confirm `main` is the production branch, the Next.js adapter and production-mode build are active, the application canonical origin is `https://playsafe.games`, and `PLAYSAFE_STAGING` is unset in the production build and functions. Keep the provider-managed production context and existing public access. Scope Supabase secrets to server functions and keep existing V1 settings.
2. After passing the database and rollback gates, review the GitHub diff against current `main` and merge with a normal release or merge commit whose message permits Netlify to build. The candidate branch commit may contain a Netlify skip marker so publishing it for review does not trigger a build. Verify that Netlify builds and publishes the intended merge revision to the existing production project. [Netlify production deploys](https://docs.netlify.com/deploy/deploy-types/production-deploy/)
3. On `https://playsafe.games`, verify the homepage, instant autocomplete and keyboard selection, a report and old-slug redirect, catalogue and public policy pages, production robots and sitemap, and the development-route 404s. Check response times, cache and popularity writes, shared quotas, and absence of staging noindex on public indexable pages. Compare against the baseline and monitor errors after publication.
4. If the release is unhealthy, republish the recorded V1 deploy and verify live search/catalogue and DNS behaviour. Prevent another release build from immediately replacing the rollback. Preserve V1 data and jobs and leave V2 objects in place unless schema removal is separately required. The V2-only down transaction and recovery sequence are in the [database runbook](HOSTED-INFRASTRUCTURE.md#production-migration-and-rollback-runbook-for-a-later-approved-release). [Netlify deploy rollback](https://docs.netlify.com/deploy/manage-deploys/manage-deploys-overview/#rollbacks)

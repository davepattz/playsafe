## Supabase staging verification

1. Confirm the staging project identity in the dashboard and confirm the PostgreSQL target independently. Use direct PostgreSQL or the session pooler where only IPv4 is available. Review `pg_trgm` placement in `public` or `extensions`, available disk and backup coverage. Verify `public` is an exposed Data API schema. Apply [the V2 migration](../supabase/migrations/20261125000100_v2_steam_cache.sql) using `psql -X -v ON_ERROR_STOP=1 -f <migration-path>`. Record migration version in the team's migration workflow so the same DDL is applied once.
2. Run the [rollback-only SQL verification](../supabase/tests/v2_steam_cache.sql) on staging. From the Data API verify anonymous and authenticated callers cannot read or write the four V2 tables or execute V2 RPCs. Verify service-role access to each intended operation and confirm role results in the logs. Check `pg_indexes` for identity, metadata expiry, catalogue prefix/trigram and limiter expiry indexes. On a populated staging table, inspect representative exact, prefix and substring query plans with `EXPLAIN (ANALYZE, BUFFERS)`.
3. Open a cold report. Confirm one `v2_game_metadata` row for the App ID/AU/English with retrieval/expiry times and expected source coverage. Repeat the report within the TTL and through a second application instance. Confirm retrieval time and Steam request counts stay unchanged. Compare the daily UTC popularity row before and after settled requests. This counts report views, including repeats. Verify Netlify preserves the asynchronous popularity update.
4. Use disposable fixtures on staging. Seed an expired complete record, inject a Steam timeout or incomplete response in an isolated test instance, and verify stale evidence, its timestamp and the previous persisted snapshot. Separately interrupt the test instance's database connection. Warm processes can serve remembered data, while cold processes can reach Steam within local budgets. Confirm the unavailable state when neither source yields a usable record. Restore the configuration on the disposable deployment.
5. Use a low configured search quota in a single minute across two independent staging instances backed by the same project. Verify HTTP 429 and `Retry-After` once the shared quota is exhausted. Confirm global limits continue locally during a database outage on each instance. A fixed window can admit a burst across a minute boundary. Same-app refresh coalescing is per process and a coverage-aware atomic write protects persistence.

**Local evidence.** The V2 migration and rollback-only permissions, RLS, cache-coverage, ranking, popularity and quota checks passed on an isolated PGlite PostgreSQL fixture. The V1 sentinel cache row survived migration and catalogue updates. Phase 6 also exercised migration down and reapply and verified two separate local Next.js processes sharing the SQL limiter, with 200, 200 and 429 results. This confirms coexistence with the checked-in V1 design. The live V1 schema, grants, job inventory and Supabase gateway behaviour still require an owner-led read-only inventory and staging verification. ## Steam catalogue import and synchronisation

1. From a private scratch directory, with the Valve key injected by a credential store, run `node <repo>/scripts/export-steam-catalogue.mjs` and save stdout as **UTF-8** `steam-catalogue.csv`. In Windows PowerShell 5, launch the redirect via `cmd.exe` or use explicit UTF-8 output, because its normal `>` can produce UTF-16. Capture elapsed time, exit status and file size. Confirm successful traversal, a plausible distinct ID count, English title coverage and a representative sample. Discard partial output and investigate abrupt count changes before promotion. Avoid printing key-bearing request URLs.
2. Set connection parameters for the verified staging project using `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGSSLMODE` and the secure credential store. From the CSV directory run `psql -X -f <repo>/supabase/import-steam-catalogue.psql` with PostgreSQL 15 or later. The importer validates the CSV header, IDs, names, uniqueness and nonempty input inside one transaction. It upserts only global `*/*` rows and preserves regional observations. It emits elapsed SQL timings, row count, total table bytes and index bytes. Record count differences, then analyze the staging catalogue so query plans use current statistics.
3. Verify exact and prefix ranking and an indexed substring query. Verify a sparse local result merges with live Steam and preserves local results when Steam is unavailable. Title-only import results do not prove Australian listing availability. Confirm import and autocomplete leave `v2_game_metadata` unchanged. Open an uncached report and check its per-app row appears only after successful retrieval with usable source coverage.
4. Start with a full catalogue sync **every two weeks**, outside peak traffic, under one runner with no overlapping imports. The 30-day observation window leaves room for a failed run and a retry. Keep the last validated snapshot and alert on failure or a sudden count change. The current importer leaves removed entries to age out of search after 30 days. Periodically review stale-row storage and PostgreSQL autovacuum. Add incremental runs only after validating Valve's modification watermark and continuing periodic full reconciliation. No hosted schedule was installed.

**Local scale measurement.** A 100,000-title synthetic CSV was 4,166,788 bytes. First import took **4.96 s** and used **33.9 MB** including **19.7 MB** of indexes. An immediate full refresh took **6.02 s** and used **59.2 MB** including **30.9 MB** of indexes before maintenance. The fixture used PGlite's blob COPY transport for the repository's SQL transaction. It checked regional precedence, rename/update, duplicate and empty import rollback, and zero detailed metadata rows created. Hosted wall time, actual Valve row count, `psql` network throughput and long-term table/index growth remain unmeasured.

[Netlify protected deploys](https://docs.netlify.com/deploy/protect-deploys/) · [Next.js adapter](https://docs.netlify.com/build/frameworks/framework-setup-guides/nextjs/overview/) · [Function limits](https://docs.netlify.com/build/functions/configuration/)

Cold container starts and cross-region PostgREST latency are unmeasured locally.

**Local production-mode smoke test.** With live Steam and V2 persistence unconfigured, the Stardew Valley report took 1,044 ms cold and 27 ms on repeat. Portal autocomplete took 594 ms cold and 12 ms on repeat. Eight concurrent first requests for Portal 2 succeeded in 406–407 ms. These are full-response localhost measurements. Reports returned private/no-store cache directives and autocomplete returned no-store. Home, sitemap, robots, news, API and report routes held the staging header. The development routes returned 404, Analytics and Disqus were absent, and a configured loopback legacy cache sentinel received zero calls when the catalogue loaded. The Netlify access gate and its CDN headers still require hosted verification.

Use Netlify's team usage dashboard to verify the active billing model. For planning, 10,000 dynamic requests at an assumed 1 GB and 300 ms each are about 0.83 GB-hours of function compute. At 80 KB per response they also transfer about 0.8 GB before assets or compression. Hosted charges also depend on CDN traffic and deployment usage. Supabase usage depends on cache hit rate, refresh and retry activity, retained snapshots and counter volume. Cold reports can use up to five Data API calls. Autocomplete can add a catalogue write after Steam fallback. Keep first-day usage alerts and compare against staging measurements before selecting launch budgets.
